# 玻尔组件搭建与文档

`bohr-component-docs` 是面向玻尔（Bohrium）组件库建设与维护的 Agent Skill。它指导 Agent 从 Figma 现有设计中抽取、搭建原子／组合／业务组件，补齐状态与属性，并整理有来源、可编辑、可验收的组件说明和业务案例。

它是一套执行规则与证据检查方法，需要 Agent、Figma 工具和文件权限配合使用。安装后不会自动改画布、发布组件库，或让已有组件直接变成“验收通过”。

## 适合什么任务

| 你的任务 | Skill 会做什么 |
| --- | --- |
| 从现有设计中抽取组件 | 读取来源、确认组件职责与依赖，按原子 → 组合 → 业务场景建立或复用组件 |
| 补齐状态和属性 | 核对已有变体、Boolean 等属性、默认值与可见差异，创建真实实例验证 |
| 整理中文组件说明 | 沿用指定模板，保留英文原稿和技术标识，补齐身份、属性、用法、场景与验收信息 |
| 补 Web／桌面业务案例 | 分端取源，整理必要元素及其关系，以完整业务片段交付可编辑实例 |
| 统一命名 | 区分双语说明标题、英文技术路径、实例名称和布局图层职责，保留 ID/key 与引用链 |
| 排查图标、变量和主题 | 核验图标资产来源、功能语义、实际绘制颜色、尺寸、Light/Dark 与父层覆盖 |
| 复核现有组件是否完成 | 按实际任务逐项检查证据，分别报告已通过、未通过、未验证和不适用 |

仅用已有组件进行选型、组合和业务页面设计，可使用独立的 [Bohr-Design](https://github.com/isawang2023/Bohr-Design)。本 Skill 侧重组件本身及其文档的建设、整理与验收。

## 安装与准备

### 1. 安装完整 Skill 目录

下载或克隆本仓库，将完整的 `skills/bohr-component-docs/` 安装到所用 Agent 的技能目录。Codex 可复制到 `~/.codex/skills/bohr-component-docs/`；覆盖旧版前先备份，并在新会话确认技能可用。其他 Agent 按各自技能安装方式操作。

入口是 [SKILL.md](skills/bohr-component-docs/SKILL.md)。不要只复制这一份文件，`references/` 和 `scripts/` 中的规则与检查工具也需要保留。不支持技能安装的工具可以读取入口，再按任务读取引用文件。

GitHub 更新不会自动同步本机安装副本；复制成功也不等于当前会话已经重新加载。

### 2. 准备工具和访问权限

- 可读取、编辑目标文件的 Figma 工具，以及目标 Figma 文件／节点链接。
- Figma 操作所需的 `figma-use` 技能；创建可复用组件时还需 `figma-generate-library`，其他操作按入口要求加载对应依赖。
- 使用本地证据校验脚本时需要 Python 3。
- 若任务包含真实 Web／桌面案例，需要能访问相应业务页面或桌面应用，并取得可追溯的原始观察记录。

依赖不可用、字体缺失或访问受限时，Agent 应明确报告受影响项，继续完成独立可做的部分，不能用替代产物冒充正式交付。

### 3. 明确任务输入

建议至少提供以下信息；已有明确约定可以直接复用，无需重复填写。

| 输入 | 内容 |
| --- | --- |
| 目标 | 组件名称、Figma 文件与目标节点链接 |
| 工作范围 | 只读盘点、局部修复、状态补齐、完整文档或业务案例 |
| 来源 | 原组件、现有业务设计、Web／桌面业务入口 |
| 模板 | 指定文档模板及需要保留的现有结构；Bohrium 文件按 Skill 已约定的 Button 模板执行 |
| 产物 | Figma 画布组件页、Markdown 专文，或两者都需要 |
| 约束 | 允许修改的中文区域、受保护原稿、平台、主题、字体和已批准例外 |

## 怎么调用

在支持 Skill 的 Codex 会话中，可显式使用 `$bohr-component-docs`。以下提示中的链接与节点需替换成实际目标。

### 只读盘点与验收

```text
使用 $bohr-component-docs，检查这个 Figma 组件：[链接]。
先只读盘点组件、属性、状态、真实实例及文档，列出有证据的缺项。
分别说明已通过、未通过、未验证；不要修改画布。
```

### 搭建组件或补齐状态

```text
使用 $bohr-component-docs，从这些源节点搭建或补齐 [组件名]：[链接]。
按原子、组合、业务场景梳理依赖，复用现有库组件与变量。
保留英文原稿，在指定中文区域操作；完成后创建真实实例验证属性和状态。
```

### 整理中文组件说明

```text
使用 $bohr-component-docs，整理 [组件名] 的 Figma 中文说明：[链接]。
沿用已指定的文档模板，身份标题保留英文组件名和中文名。
补齐属性、基础用法、场景规则及待确认项，并读回验证。
本次交付 Figma 组件页，不额外生成 Markdown 专文。
```

### 补齐真实业务案例

```text
使用 $bohr-component-docs，为 [组件名] 补充 Web 和桌面的真实业务案例。
Figma 目标：[链接]；业务入口：[入口]。
分别取源，登记必要元素、业务关系和完整组合；使用真实组件实例。
不要把单独控件或主题副本算作完整业务案例。缺来源时保留未验证状态。
```

### 整理给后续代码读取的专文

```text
使用 $bohr-component-docs，为 [组件名] 输出 Markdown 组件专文。
记录来源节点和 key、英文技术标识、属性默认值、组合规则、案例及验证边界。
所有实际数值关联取源记录；本次不改 Figma 画布。
```

若希望在工作区持续执行调用规则，将本仓库 [AGENTS.md](AGENTS.md) 中的约定加入该工作区支持的项目指令。安装 Skill 本身不保证每次自动触发。

## 会交付什么

交付范围由任务决定。局部图标修复不需要顺带重建整页；只要求 Figma 文档时，不自动增加 Markdown 专文。整页整理需要覆盖下列适用内容，但不要求每项单独新建画板。

### Figma 画布产物

| 产物 | 展开内容 | 完成依据 |
| --- | --- | --- |
| 组件资产与状态展示 | 原子／组合／业务组件，已有与新增属性、变体和必要状态，清楚的布局与状态标签 | 主组件与默认实例、属性编辑、状态覆盖及引用关系有实际检查 |
| 中文组件规则 | 中英文身份标题、用途、适用与不适用范围、选择依据、关联组件、边界和待确认项 | 使用指定模板；事实、线上观察、建议和待确认内容分别标明 |
| 基础用法与示例 | 可编辑真实实例、属性组合、正常与边界用法、适用主题对照 | 实例可追溯，变量及布局关系保留，按范围完成重排检查 |
| Web 业务案例 | 来自 Web 的用户任务、必要控件、业务上下文及操作关系 | 有独立来源记录，完整组合与各元素逐项对应 |
| 桌面业务案例 | 来自桌面应用的任务、必要控件及关系 | 与 Web 分别取证；不能直接沿用 Web 结论 |
| 验收结果 | 产物链接、检查范围、通过项、缺口及恢复条件 | 对应真实读回证据；维护日志放本地，不塞进面向设计师的正文 |

**业务案例的验收单位是完整业务片段。** 例如问题反馈场景，需要根据真实来源组织问题输入、日志授权 Checkbox、提交操作及其关系。仅放一个 Checkbox、标题和说明，只能算控件映射，不能算反馈案例完成。附件、必填规则、禁用条件等必须有来源，不能为“补完整”自行编造。

Light/Dark 是同一案例的主题对照，不是两个不同业务场景。已有设计、线上观察和本次示意也分别记录，不能混作线上运行证据。

### 命名与代码定位

| 对象 | 示例／要求 |
| --- | --- |
| 中文组件页面与身份标题 | `Checkbox / 复选框` |
| 规则文档根名称及标题 | `Checkbox Rules / 复选框规则` |
| 示例文档根名称及标题 | `Checkbox Examples / 复选框示例` |
| 主组件与技术属性 | 保留 `Checkbox`、`Checked=No`，不因中文化改动 |
| 布局与文字图层名称 | `Content Row`、`Title`、`Description` 等职责名 |
| 业务案例容器 | `WEB-01 / Feedback / 问题与反馈 / Light` |

双语标题方便搜索和理解；后续代码定位优先依据节点 ID、组件 key 和实例引用链，不通过拆分标题猜测组件路径。英文标识保持原大小写，例如 `InputGroup` 不改写成 `Input Group`。详见 [Figma 命名规则](skills/bohr-component-docs/references/figma-naming.md)。

### Markdown 组件专文（任务要求时）

专文按以下六部分组织，通常使用 `references/components/<稳定英文名>.md`，并维护对应组件索引：

1. **身份、来源与状态**：检索别名、file/page/node ID、组件 key、读取日期、平台、主题与已知缺口。
2. **组件属性与变体**：属性键、类型、可选值、默认值和变体轴；未暴露的能力明确注明。
3. **选择与组合规则**：何时使用、何时不用、与相似组件的区别及组合方式。
4. **已有设计案例与边界**：正常与边界用例、来源、验证结论及适用限制。
5. **验证范围与待完成**：内容、形式、场景、图标来源与颜色等分项状态。
6. **取源与缺口**：原始证据位置、未通过项的归属和恢复条件。

专文服务于事实检索和规则读取，不套用 Figma 画布的排版模板。组件索引的位置需按工作区实际依赖核对；本仓库不包含另一个设计语言仓库的完整索引。

### 本地验收记录

| 记录 | 内容 |
| --- | --- |
| `contract.json` | 锁定任务范围、参照、适用检查项；业务案例另列场景、必要元素及关系映射 |
| 原始证据文件 | Figma 工具读回或分端业务观察，保留可定位内容；与人工摘要分开存放 |
| `report.json` | 每项实际结果、目标节点、状态、当前版本和证据摘要 |
| `check-result.json` | 校验器对缺项、记录差异、版本及证据引用的检查结果 |

按 [任务清单与证据记录](skills/bohr-component-docs/references/task-evidence.md) 生成记录后，可在仓库根目录运行：

```sh
python3 skills/bohr-component-docs/scripts/check_evidence.py path/to/contract.json path/to/report.json > path/to/check-result.json
```

退出码 `0` 表示记录校验通过，`1` 表示存在缺项、差异或未通过／未验证项，`2` 表示输入无效。脚本不会连接 Figma 自动审图，也不能认证来源真实性、发现所有漏列场景，或阻止 Agent 跳过检查。记录通过后仍需结合实际产物判定。

## 怎么判断任务完成

检查范围包含适用的原稿保护、内容、模板形式、实例与可维护性、端侧来源、图标来源及实际表现、视觉等项目，详见 [统一验收门槛](skills/bohr-component-docs/references/acceptance.md)。

- **已通过**：本次范围有充分证据支持。
- **未通过**：已经观察到不符合要求的情况，需要修复。
- **未验证**：尚未检查或缺少决定性证据，不等于通过。
- **不适用**：确实不属于本次范围，必须说明理由；不能把受阻项改成不适用。

任一适用必检项未通过或未验证，整体只能按已完成范围报告部分完成。字体缺失、实例无法嵌入或来源访问受限会改变完成状态，不会降低交付标准。临时字体替代需要明确授权，并保留正式字体验收缺口。

包结构检查、记录校验、Figma 实际产物验收、Web／桌面运行验证、组件库发布、Skill 安装及宿主加载是不同状态，不能相互替代。上传、提交等真实业务操作也不因整理案例而自动获得授权。
