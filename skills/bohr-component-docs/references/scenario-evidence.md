# Web／桌面端场景证据与规则对齐

## 采集记录

先列Web与桌面的取源任务，再按真实入口执行。每端记录已检查位置、操作、日期和结果；未检查、未找到、不可访问分开记，某一控件的工具故障不证明另一控件或整端已检索。仅桌面缺失不能抹掉已证实的Web工作，也不能用Web通过抵消桌面缺口。

**原始观察与整理结论分开保存。** 案例结论引用可复核的工具原始返回/操作记录及其中的具体位置；可用脱敏文本，不以截图为前提，遵守用户不截图约束。自写报告、Figma文案或标为“实际案例”的标题不独立证明线上访问。历史证据可复用，但核对对象、范围、日期与当前有效性；找不到原始记录时降为待复核或重新取源，不补写“已验证”。

每个场景分配稳定ID，关联「线上证据 → 规则段落 → 可编辑案例节点」。规则和示例可分开存放，但导航及映射必须可定位。案例须保留任务、触发条件、周围标签/操作、输入前后状态和组件组合关系；单个Item/List实例可解析不证明重现了线上组合。分别注明线上观察、库组件映射、本次示意，设计扩展的Dark版本不得称线上Dark已核验。没有证据就保留缺口并继续其他可做项，不能只补通用文案结束取源步骤。记录格式见 [任务清单与证据记录](task-evidence.md)。

| 字段 | 内容 |
| --- | --- |
| 场景编号 | 当前任务内稳定编号 |
| 产品／端侧 | Web、桌面端或未确认；版本、环境、操作系统按可取得信息记录 |
| 页面入口／对象 | 页面位置、入口路径、业务对象 |
| 用户任务 | 用户想完成什么 |
| 条件／阶段 | 前置条件、任务阶段、空间条件、权限条件 |
| 组件关系 | 目标组件与标签、容器、其他操作的关系 |
| 状态与行为 | 默认、悬停、聚焦、加载、错误等；区分观察与推断 |
| 证据 | 链接、节点、截图或操作记录、采集日期 |
| 覆盖边界 | 哪些状态未检查、另一端是否检查、仅静态还是实际操作 |

只收集该任务需要的界面，截图及示例避免暴露个人信息、密钥、私人文件内容。对线上操作保持任务范围，不通过付费、删除或发送内容来验证普通示例。

## 对齐方法
1. 先按操作目的归组，如提交任务、确认操作、选择内容、切换视图。
2. 再比较共用语义与端侧差异：同目的不要求同布局；系统能力、导航、窗口空间等可能合理不同。
3. 最后补适用条件：任务阶段、内容密度、异常状态与操作数量。
4. 区分四种对照结果：
   - 两端一致：证据覆盖的相同条件下表现一致。
   - 合理差异：有明确规范、能力限制或产品决定支持；只有观察差异时不能直接称合理。
   - 待确认差异：表现不同但缺少选择依据。
   - 仅一端存在：在明确范围内确认另一端没有对应入口；未查到不足以证明不存在。
5. 形成“条件 → 选择 → 原因 → 例外”的规则，并关联来源。

## 案例选择与说明

### 可编辑业务片段的交付结构

先从实际来源锁定最小业务闭环：任务对象、必要输入/选项、目标组件、相关主次操作及其关系。每个必要元素都映射到画布节点，每条关系都以结构或属性读回验证；外层可以是Frame，内部控件复用库INSTANCE，不强制把整个片段再制成主组件。

反馈提交场景的最小片段包含问题描述输入、日志同意复选框和提交操作及其顺序/关联；仅有标题、来源说明、复选框时，状态为“控件映射完成／业务片段未完成”。若实际来源另有条件依赖（如附件或校验提示），按该来源登记；不能凭经验虚构必填、禁用或提交行为。无关导航可排除并记录理由，不能把完成任务所需的操作排除。

独立对照实际来源与必要元素清单，防止先漏列元素再让脚本通过。验收顺序为取源、元素对应、关系对应、组合整体、运行边界；浅深色副本不增加业务场景数。取源、控件映射、业务片段和运行验证分别报告状态。原始结构缺失时保留“未验证”，不以8个INSTANCE、绑定正确或无重叠替代场景验收。

每条关键规则先选一个代表案例；差异明显时再补另一端或边界案例。不要求每条规则都有重复的两端截图。例子应同时对齐：
- 业务任务与适用条件。
- 实际组件属性和状态。
- 周围内容、主次操作与布局关系。
- 公共样式和规则。
- 说明中给出的选择理由。

案例来源标为“线上观察”“已有设计示例”或“本次示意”。没有业务素材时可以用组件搭建示意，写清尚未在线上核验，不虚构页面或上线状态。


业务使用规则正文须给出适用条件、选择理由、关联组件边界和例外；节点编号、字体故障与维护日志留在验收记录。用户要求玻尔经典案例时，必须定位真实产品入口并记录端侧与日期；Form Examples 等原库样例不能充当实机证据。要求可复用案例时，Figma 中必须插入有主组件链的真实实例，截图只能作为观察证据。
