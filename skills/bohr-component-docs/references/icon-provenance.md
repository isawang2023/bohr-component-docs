# 图标来源与库内证据

图标是否“看起来像”不能证明它来自组件库。业务组件的每一个图标都必须能追溯到当前批准的 Bohrium 图标库实例；没有来源证据就不能进入正式示例。

## 硬规则：参照功能，使用玻尔资产

- 适用范围包括中文组件、基础用法示例、业务案例、浅深主题及隐藏状态。英文原稿保持不动；英文图标仅用于识别功能、状态、方向和位置，不能成为中文版本保留原图标库的理由。“严格对照英文”“以英文 icon 为准”不构成沿用 Lucide、HugeIcon、Material 等来源的授权。
- 替换前建立逐项映射：原节点与功能 → 玻尔候选 → 选择理由 → libraryKey/componentKey → Wrapper 属性值 → 主题、尺寸及颜色变量。不能批量将不同功能收敛为搜索、箭头或任一默认图标。
- 来源和语义是两个独立硬门槛。必须结合上下文与实际图形核对可识别性：密码显隐用眼睛状态；邮箱用信封；支付卡用卡片；复制用复制图形；刷新与加载分别表达；普通勾选与带圆形背景的确认保留状态区别；代码文件不得替换为搜索。相近名称或引用成功不等于功能匹配。
- 对照参照不是逐像素复刻外库图形。采用玻尔对应图形，保留原用途、状态、方向、图标槽尺寸及位置；保持原组件可编辑、实例关系和颜色变量。功能无法明确对应时标记“待确认映射”，不得宣称完成。
- 库检索失败记“库检索未完成”；检索完成但无对应资产记“缺少语义对应资产”。两者均阻断该项，不得使用原图标、占位图标、手绘或 SVG 绕过。可完成其余已确认项，缺口单列。
- 验收必须同时检查：逐项语义、Wrapper 及最终主组件 key、所有有绘制作用的 fills/strokes 颜色绑定、尺寸与父层缩放、浅深主题和显隐状态。不得用截图相似或文字翻译通过代替图标验收。

## 红线：颜色变量

图标来源通过不等于颜色通过。所有实际参与绘制的可编辑图标 `fills/strokes` 必须绑定组件库的图标颜色变量，并记录变量 ID、变量名称和主题/状态模式。硬编码颜色、未绑定 Solid Paint、隐藏的白色覆盖值或只设置节点 opacity 都是阻断项。库实例内部不可编辑的路径由库维护；业务组件的合法颜色覆盖必须完成变量绑定；此条不授权自绘图标替代库实例。

## 引入后强制检查

本节在创建实例、INSTANCE_SWAP、尺寸调整或主题变更后必做。仅检查源码/主组件不算完成；每个相关实例必须有写后读回证据。先记录预期来源，再判结果，不用当前错误值反定规范。

颜色不一致时按 [颜色保真与最小修复](icon-color-workflow.md) 执行，分别验收语义绑定和主题继承，不以清除 Dark 后看起来同色作为完成证据。

1. **描边只按批准尺寸策略缩放一次。** 对照源组件尺寸与实际 `strokeWeight`、绑定变量 ID、当前模式解析值、Wrapper 尺寸、内部实例/矢量尺寸、父层变换和最终实际 `strokeWeight`。变量解析值不等于最终画布值；尺寸模式已经给出最终描边时，不能再乘一次实例缩放。必须按批准的缩放链计算预期最终值，再与实际值比较；变量解析值与最终描边不同本身不构成失败。超出预期需沿主组件链查缩放/覆盖并阻断，不只检查变量存在。固定描边、随尺寸缩放或其他策略须有源依据；无依据记未验证，不自行设定全库线宽。纯填充图标的描边项可不适用，但要记录原因并检查填充几何。
2. **外框与内部几何分别验收。** 比较实际槽位、Wrapper、内部图形的宽高、比例、位置及父链缩放；外框 16×16 不证明内部比例或线宽正确。保留批准图标的笔画、端点/连接样式和细节，不用放大内部路径抵消父层错误。
3. **颜色绑定必须符合功能语义。** 记录源和最终实际绘制 fills/strokes 的变量 ID/名称、别名解析链、主题/状态解析值、Paint opacity、节点及父层 opacity。不能把 `color/icon/context`、错误/链接/禁用等语义无差别替成 `icon/default`；如组件规范要求合法覆盖，记录该依据。相同 RGB 不证明语义绑定等价；变量存在也不证明状态正确。空 fills 无绘制作用不需补绑定，专用多色资产保持配色。
4. **核对主题继承的实际结果。** 同时读取语义容器的预期 Light/Dark、collection/mode ID、父层与实例 `explicitVariableModes`、最终 `resolvedVariableModes`、实际颜色解析值及背景；查清哪一层覆盖生效。Light 容器中实例显式锁定 Dark 即失败。局部主题反转只有当前组件规范明确允许时才合法；不能只按容器名称、截图或“两个模式都能解析”放行。
5. **覆盖全部受影响状态。** 枚举本次相关尺寸/变体、Light/Dark、禁用/错误等实际存在的状态及隐藏图标。Plugin API 遍历前显式设置 `figma.skipInvisibleInstanceChildren=false`，仍须验证已知隐藏节点确实进入清单。记录范围与数量，保持前后统计口径一致。默认实例通过不能替代全体；不制造不存在状态，不将局部修改扩大为全库改造。

检查结果按“源节点 → 目标节点 → 预期依据 → 变量及模式解析 → 最终描边/几何/颜色 → 差异 → 状态”逐项记录，配同倍率局部截图。数值比较默认只允许浮点误差：描边绝对差 ≤ 0.0001px、几何 ≤ 0.01px；这是读取误差阈值，不是视觉偏差许可，不得用取整把 0.8 当 1.2。更宽的设计容差须有批准依据。

**统计口径必须明确。** 以本次指定根节点及其子树为范围，按Wrapper节点ID去重统计“图标实例”，不能把Wrapper、内部Icon实例和矢量路径重复相加。报告同时列总实例数、可见实例数、隐藏实例数；隐藏判断检查从实例到根的完整祖先链（不能在遇到Light/Dark容器时提前停止）。此处可见仅表示visible链成立，不等同于视口内、未裁切或opacity非零。不同图标种类按最终图标主组件key去重，key不可取时按文件+主组件ID并说明；无法追溯项单列，不能按名称或实例数冒充种类数。浅深主题、多个示例和隐藏状态中的重复引用各算一个实例。统计不是新增数量，未新增时不得称“创建了N个图标”。给用户总数时同时附Figma根节点链接和显隐拆分，不只给裸ID。

若失败，只修本次获授权实例或隔离专用组件；保留绑定和原生实例，禁止 detach、硬编码线宽/颜色掩盖问题、整树 resetOverrides 清掉用户内容，或改共享主组件/变量影响英文。不能隔离或缺少合法策略则阻断该项。修复后重新执行相关尺寸、主题、隐藏状态检查，再次 swap/重复执行不应再次变细或错色。

24→16、变量 1.2 而最终 0.8，以及 24→12、变量 0.9 而最终 0.45，是需要检出的重复缩放示例，不是所有图标必须采用这些线宽。仅数值比例吻合可记疑似重复缩放；未有属性、变换或受控复现证据，不声明具体工具根因。

### Bohrium Scale 操作基准（2026-11-02 用户确认）

执行步骤与重复操作检查见 [Scale 生成与验收](icon-scale-workflow.md)。

以 [正确缩放样本 28706:20773](https://www.figma.com/design/SmWwL4eUrBlNQAG6nfWqll?node-id=28706-20773) 为本套线性图标的缩放依据：保留 24px Wrapper 主组件 `26166:5464`、`Bohr Icon Size=24` 和描边 collection 的 24px 模式 `26704:0`，通过 `Bohr icon` 属性引用目标图标，再用 Figma **Scale** 整体等比缩放到目标尺寸。Plugin API 对应 `instance.rescale(targetSize / instance.width)`；已经是目标尺寸时不再次累计乘比例。不得用切换 16/12 尺寸变体、仅 resize 外框、改矢量线宽代替该流程。

本次 mail 基准：24px 实际描边 1.8px；Scale 24→16 后为 1.2px；24→12 后为 0.9px。三者仍保留 24px 描边模式，解析基值为 1.8px，验收预期是基值乘一次 1、2/3、1/2；不能因 1.8≠1.2 而误判。主组件、缩放比例、内部路径位置与尺寸、实际描边、颜色绑定及透明度均对照批准样本。此数值属于 mail 样本，不推定所有图标都为 1.8px。

修复测试行 `28705:2920` 已使用该方式；16/12px 实例替换为 `28707:2265`、`28707:2268`，原始失败证据仍保存在本地验证记录。颜色维持 `color/icon/context` 绑定，当前 Light 为 #1D2129；其他状态仍按语义与主题检查，不能硬编码此颜色。

## 批准来源

1. 先用 `figma_get_libraries` 读取当前文件可用库，再以当前团队的 Bohrium Design System 库为唯一默认来源。当前文件在 2026-10-28 读取到的库名为 `Bohrium Design System 1.0.0`；库 key、发布状态和可用性每次任务都要重新读取，不能把本记录当作永久配置。
2. 用 `figma_search_design_system` 按语义和完整名称搜索目标图标，记录返回的 `libraryKey`、`componentKey`、组件名称和查询词。搜索到的 `Icon/...` 组件只能作为 `Bohr icon/Wrapper` 的 `Bohr icon` 属性值，不能直接放到业务组件中。
3. 业务组件中的线性功能图标最终结构必须是 `Bohr icon/Wrapper` 实例，且其 `componentProperties` 中存在 `Bohr icon#...` 的 `INSTANCE_SWAP` 属性，值指向批准的 Bohrium 图标组件。`IconPlaceholder → HugeIcon`、直接 `Icon/...`、直接 `folder` 等均为错误绑定位置，即使外观正确也失败。
4. 预览中必须是可追溯的 `INSTANCE`。实例的 `mainComponent.remote`、`mainComponent.key`、组件名称和库搜索结果要能互相对应。嵌套实例要记录从业务组件到 `Bohr icon/Wrapper` 再到最终图标实例的链路。

文件类型图标等专用多色资产按批准的独立组件族引用（例如 `File icons`），不强制包装为线性图标。必须核对确切变体、主组件 key 与覆盖；其源库未绑定颜色仍单列为缺口，不能宣称全部颜色变量通过。

## 明确禁止

- 独立 `VECTOR`、`BOOLEAN_OPERATION`、`STAR`、`POLYGON`、`ELLIPSE`、SVG、图片或 emoji 作为图标交付，即使外观与库图标相似。
- 只按名称判断来源，例如节点叫 `chevron-down`、`folder` 或 `Icon`，但没有库 key 和实例证据。
- 使用 HugeIcon、Material、其他团队库或本地历史组件替代 Bohrium 图标；名称相近不代表属于批准库。
- 通过截图描摹、复制路径、detach 实例后改色或重新绘制来“补齐”缺失图标。

## 生成前与生成后的操作

生成前为每个语义图标建立清单：业务角色、目标名称、搜索词、批准库、component key、预期尺寸和替代/待确认状态。搜索不到精确图标时保留“未找到匹配”并阻断交付，不能自行猜一个。

生成后遍历所有示例及其嵌套子树，盘点所有 `INSTANCE`、矢量和形状节点。对每个图标节点记录：节点 ID、实例链路、Wrapper 主组件、`Bohr icon#...` 属性值、最终 `mainComponent.key`、`remote`、组件名称、`libraryKey` 和搜索结果。只要出现一个直接线性功能图标实例、`HugeIcon`、错误 `IconPlaceholder`、未解析实例、独立矢量或非批准库来源，图标验收即失败；应回到本次可写中文／业务组件替换（不得影响英文源组件）并重新遍历，不在文档页上覆盖一个“看起来正确”的图标。

同时读取实际绘制 Paint 的 fills/strokes 变量绑定及变量解析值；空 fills 不要求绑定。缺少 `VARIABLE_ALIAS`、变量不属于批准图标颜色集合或模式不匹配时，在本次可写中文／业务组件绑定变量（不得改共享变量影响英文）并重新检查；不能以截图颜色或 RGB 数值作为替代证据。

| 发送 | `node-id` | `Button → Bohr icon/Wrapper → Icon/Arrows/...` | `...` | `...` | `true/false（同文件主组件须核对 key 与库证据）` | 通过/阻断 |
