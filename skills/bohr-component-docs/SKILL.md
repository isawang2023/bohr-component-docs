# 玻尔组件文档整理

同一组件库的最终文档必须使用**同一信息覆盖要求、同一视觉模板、同一验收口径**。基础组件与业务组件共享模板的视觉角色与布局关系；章节主题可以适配组件，不能把语义字段强制展开为新的表格、卡片或展示板。

## 范围与授权

- 只读盘点不写画布；明确要求整理或修改时按授权执行，不重复索要已有授权。翻译任务只填相应字段，不扩大为业务规则制定。
- 保留原英文、技术标识、原组件和用户已改内容。整理文档不自动包含重命名主组件、合并组件、改属性、发布组件库或线上提交操作。
- 批量任务共用一份模板锁定记录，不能每个组件自行挑参照页面。
- 没有正式模板时，先完成内容盘点与一个可审阅的模板候选。候选确认前不批量套版，也不称为最终规范。已有明确确认直接复用，无需再次审批。

## 不可违反的红线

1. **英文原稿只读保护。** 不修改、删除、重建英文原组件和说明，不通过共享主组件、样式或变量间接改变它们。中文修改限于本次中文组件与示例；写入前记录保护范围和共享依赖，写入后核对差异。操作细则见 [原稿保护与翻译](references/translation.md)。
2. **图标必须引用玻尔资产且功能对应。** 英文仅提供功能、状态、方向与位置参照；不得沿用 Lucide 等外库、默认占位、手绘、SVG 或 detach 替代。来源与语义分别验收；无明确对应资产时阻断该项，不猜测。
3. **真实实例和绑定不可伪造。** 验证主组件链、Wrapper 属性、实际绘制的 fills/strokes 变量、主题、尺寸及父层覆盖；批准的文件类型多色资产保留专用组件和配色。库实例内部矢量不是独立自绘替代，须沿实例链判断。
4. **业务规则与案例必须有据。** 规则说明何时用、为何用、选择边界与例外；原库样例不冒充玻尔业务案例。Web 与桌面分别取证；示意、观察、建议和未验证明确区分。
5. **指定模板与完整性不可降级。** 按任务范围核对分区、矩阵、属性、真实案例、导航与主题；不自创展示板、不静默换字体、不用截图代替可编辑实例。局部任务不扩大为整页改造。
6. **未验证不得放行。** 英文保护、图标来源/语义/颜色、实例、模板及主题分别报告；任一适用红线失败或缺证据，不能称整体合规。静态检查不等于真实生成、运行或发布。

## 固定交付约定

组织或修改文档前读 [内容与视觉模板](references/document-template.md)，确定模板来源、版本、状态及实际样式值。**源组件是能力和案例来源，不自动成为文档模板。** 无英文原稿也使用同一模板，并标注“新增整理”。

内容必须覆盖：身份与来源、**属性与变体、基础用法与示例、业务场景与规则**、验收与待确认。这是信息要求，不是五个可见章节，更不等于三张展示板。先映射到模板已有位置；维护状态与报错放本地记录，不占据使用者文档正文。

当前 Bohrium 文件已由用户指定 Button 为参照，必须读取 [Button 模板配置](references/bohrium-button-template.md)，分别复用“中文规则与实际案例”和“基础用法与示例”。不得改用 Input 或上一版 Composer 自制展示板，也不重复询问同一参照。其他库采用其指定模板，不套用此处数值。

## 整页完整性（强制）

本节用于整页整理、形成组件规范或补齐文档。只修改某个图标、属性或一条翻译时，仅检查该修改影响的项目，不要求补建整页；适用的来源、绑定与保护红线仍须检查。

Bohrium 的 Components 必须使用 Button `296:5340` 的行列标签与单元格矩阵形式，并核对 Accordion `34:526` 的完整轮廓。Composer 主区仅放基础元素，组合与业务组件、对话任务进度分别收纳；长说明放文档。按各分区比较实际变体与展示清单，主动补齐遗漏及有可见差异的 Boolean 属性，不将全量覆盖误做全量混排。

浅色／暗黑对照是完整文档的必检项：沿用 Field `18748:157934` 的 Light / Dark 真实实例与变量模式结构，不能只换背景。写入后读回模式、语义变量解析值和嵌套背景；对照案例必须一致，未通过项明确记录。

用户要求形成组件规范、对齐其他组件说明或补齐文档时，先读 [整页区域与导航验收](references/page-completeness.md)。必须检查参考 page 的顶层区域，不能仅比较规则和示例两份文档。Components 资产区、元素说明、属性与状态标签、真实实例、导航链接均纳入差异清单；不存在的属性明确写未暴露。

## 组件命名与唯一路径（强制）

涉及组件创建、组件整理或用户授权的命名修复时，必须先读取目标组件族及库内代表组件的实际名称、组件集和属性，记录参照节点；不得自行发明另一套路径。组件构建同时加载 `figma-use` 与 `figma-generate-library`。

- **完整组件路径是查找入口，必须唯一。** 在同一库范围内，组件集或独立主组件的完整名称必须唯一；组件集内由「完整组件集路径 + 完整变体属性键值」唯一定位。页面名、外层 Frame、截图相似或 node ID 不能补救重复或错误路径；ID/key 仍须记录以验证引用。
- 沿用库内族名、大小写、分隔符和子组件层级；业务 Composer 不得误挂在基础 Input 下。Bohrium 当前依据为 `Input`、`InputGroup / Addon Inline`、`Field / Separator`：子组件采用 `族名 / 子组件`；中文说明放页面或说明字段，不混入技术路径。该例仅适用于此库，其他库读取其自身约定。
- 库内已有 `State` 等维度时，同族同职责的状态必须用组件集变体表达（例如 `State=Default`、`State=Focus`、`State=Disabled`），不得另造 `/ Inactive` 或 `/ Disabled` 独立入口；内容、焦点与禁用是不同含义，不因名称相似而混为一态。
- 创建前检索完整路径，存在则定位复用；重复执行不能新建同路径组件。重命名之前记录「旧路径 → 新路径 → node ID/key → 引用实例」，保留主组件与实例关系，不用删后重建实现改名。只读文档任务不得借本规则擅自重命名或合并主组件。
- 交付前检查库范围内路径冲突、组件集内重复属性组合、所属 page、默认变体以及实例主组件链路；更新受影响的路径索引和说明。未读全的范围必须标注，不能声称全库唯一；任何目标路径冲突、错族或无法定位均阻断命名验收。

- **命名验收必须递归覆盖嵌套依赖。** 从最终业务实例沿 mainComponent 链检查全部本次自有主组件及其所在 page，不能只统计外层组件集。主组件使用库内完整唯一路径；实例对齐其主组件名称；普通 Frame 使用 Content Row、Bottom Row 等职责名，不能遗留 Frame 数字或冒充组件入口。业务文案放 characters，不用文案命名主组件；库外或共享库内部命名不擅自改动。主组件无法解析或没有 page 归属时单列依赖缺口，不通过改实例名称掩盖。

## 组件抽取与搭建

用户要求从现有设计抽取、搭建或补齐组件状态时，必须先读 [组件抽取与状态验收](references/component-extraction.md)，并加载 `figma-use`、`figma-generate-library`。先明确本次组件清单与职责，再创建依赖和场景实例；组件文档模板不替代组件构建流程。交互状态、执行状态、内容与展开分开建模；交付前必须创建真实实例验证默认值、属性编辑、引用链和颜色绑定，不能只检查主组件截图。

## 工作流程

### 1. 读取来源并锁定模板

读取目标实际文字（含嵌套实例）、单体组件、组件集、属性默认值、已有中文文档和公共规范。记录来源、日期、范围；大页分区读取，不能以截断结果代表完整检查。

按模板规则锁定同一份版式与结构，核对字体和复用路径是否可用。写入前复核目标区域与用户改动；已有文档按节点更新，不重复创建新版展示板。

### 从现有模块抽样组件

当来源不是单个组件，而是已有页面或业务模块时，先做抽样盘点，再决定文档归属：

1. 记录来源文件、页面/Frame、节点 ID、平台、主题、读取日期和抽样目的；不能只凭截图或模块名称判断组件来源。
2. 按“模块容器 → 业务组合 → 基础组件 → 嵌套实例/图标 → 属性与 Token”逐层检查，记录节点类型、主组件链路、组件集属性、实际取值、状态和布局约束。
3. 将结果分为：可独立复用的基础组件、由多个组件组成的业务组合、面向页面区域的模块预设、只在该模块成立的局部例外。
4. 基础组件进入对应组件专文；跨组件的组合关系进入场景案例；模块预设和局部例外保留在来源记录，不自动升级为公共组件规则。
5. 每个候选至少覆盖一个正常状态、一个内容变化或长文本状态，以及一个实际存在的边界状态。同一组件集有多个变体时，不能只抽样默认变体。

抽样只证明来源中观察到的现状，不自动证明组件已发布、代码可调用、线上行为已验证或适合全库复用。无法追溯到主组件、已 detach、仅复制外观或仅有截图的对象，标记为“未验证的视觉模式”，不能写成“已复用组件”。

### 2. 填充统一内容

按模板字段填来源事实、能力、案例与规则；属性不存在写“未暴露”，证据不足写“未验证”，不构造空属性或伪造案例。只读任务也按相同字段输出内容草稿。

涉及图标时先读 [图标来源与库内证据](references/icon-provenance.md)。**英文或外部参照只定义功能语义、状态与位置，不授权沿用其图标库。中文组件、基础示例、业务案例及隐藏状态均必须在玻尔库中查得语义对应的资产，再通过 `Bohr icon/Wrapper` 的 `Bohr icon` INSTANCE_SWAP 属性引用。不得将“以英文为准”解释为复制 Lucide、HugeIcon 等原图标。图标来源正确但无法辨认原功能同样不通过；搜索、复制、刷新、加载、密码显隐、信息提示等不得混用。** 直接放置 `Icon/...`、`HugeIcon` 或 `IconPlaceholder` 不视为合规结构。生成后必须遍历示例及嵌套子树，发现独立矢量、非批准库实例、错误包装层、无法解析的包装层或语义不匹配就阻断该项并修复本次中文／业务组件；不得直接或通过共享依赖改变英文原组件。文件类型等批准专用资产按正式组件族引用，例外边界见组件抽取规则；不得覆盖其多色语义。没有明确对应资产时记录缺口，不得保留原库图标、默认占位图标或猜测替代。

**引入后强制验收：** 每次创建、swap、缩放或主题变更后，按 [图标引入细节检查](references/icon-provenance.md#引入后强制检查) 对照源图标、Wrapper 与最终实例的实际描边、变量解析值、内部几何、父层缩放、颜色语义和主题继承，覆盖相关变体及隐藏状态；任一项失败或未验证均阻断引入完成。不能以来源正确、外框尺寸正确或存在绑定替代检查。

**红线：图标颜色必须引用组件库颜色变量。** 检查实际参与绘制的 `fills` 和 `strokes` 的变量绑定、变量 ID 及主题/状态解析值；无绘制作用的空 fills 不要求伪造绑定。硬编码颜色、未绑定绘制 Paint 或仅靠截图模拟均失败。专用多色资产保留源配色，源库绑定缺口单列，不擅自重着色或称全项通过。

翻译前读 [术语与翻译规则](references/translation.md)。保留英文原稿、属性键值、变量、代码、版权与链接；中文逐项对应。无英文说明时标新增整理，不能称翻译完成。

规则分别标识：已确认规则（注明适用范围）、观察到的现状、整理建议、待确认。样例限额、时长、日期和状态名不能直接成为业务规则。

### 3. 对齐场景与关联组件

涉及业务场景时读 [场景证据与规则对齐](references/scenario-evidence.md)；涉及组件选择边界时读 [公共依据与关联组件](references/shared-rules.md)。按操作目的归纳“条件 → 选择 → 原因 → 例外”，关联代表案例或明确的证据缺口。

Web 与桌面端分别记证据及检查范围。无有效线上访问时继续整理有依据的内容，在固定对照字段标未验证；不得删栏目、编造一致性或拿设计样例充作上线事实。

### 4. 按锁定模板写入

写入前读 [执行检查与失败恢复](references/execution-checks.md)：先在授权范围跑通一个代表单元的实际操作和读回，再扩展数量；按实际修改建立检查记录，不额外扩大任务。

复用模板的布局、样式、变量和预览容器；英文原稿保留，中文在约定位置。优先复用真实 Header、Preview、Footer 等结构。无法复用而重建时必须逐层比较，不只仿页宽和字号。章节标题、案例标题、属性注释分别匹配各自角色，不能提升子标题层级。预览使用真实实例，说明与实例保持可维护的布局关系。

缺字体、无法嵌入实例等限制只改变完成状态，**不改变交付标准**。禁止自行换字体、用链接代替必需预览、用截图代替可编辑示例，或以页面级绝对定位叠放实例冒充模板完成。普通编组只能解决移动，不能证明文本增长时能正确重排。

受限时保留原稿，继续盘点、内容与其他不受影响项；受影响部分留在工作稿并写明恢复条件，不能升级为规范完成。只有用户明确批准变更模板时才调整标准，同时记录新版本与其他组件的迁移范围；披露偏差本身不等于批准。

### 5. 验收与交付

读 [统一验收门槛](references/acceptance.md)，形成“参考节点 → 目标节点 → 角色 → 差异 → 修复结果”记录，核对完整属性与嵌套结构，再检查同倍率截图。检查字重、颜色解析值、paint opacity、节点及父层 opacity，不能遗漏内容边界线、预览分隔线和页脚对齐轴。局部修复后复查受影响部分；脚本成功、文字齐全或无重叠均不足以证明与 Button 一致。

返回结果链接、模板版本、完成范围与剩余缺口。先给任务整体状态，再列局部通过项；整体状态按验收记录中全部适用项判定，缺证据不记通过。分别报告内容、形式、场景验证、图标来源和图标颜色变量验证；任何图标颜色红线未通过都必须报告为阻断，不能称“按规范整理完成”。不将整理完成等同于发布或运行验证。

## 工具与技能验证

使用当前可用的官方 Figma 工具；Plugin API 操作遵循 figma-use，创建组件或多区块布局时加载对应技能。工具不可用时明确本地草稿与远端交付的区别。

修改本 Skill 或检验跨组件一致性时使用 [验证方案](references/validation-plan.md)。静态校验只证明包结构；真实生成、重排和重复执行另行取证。
